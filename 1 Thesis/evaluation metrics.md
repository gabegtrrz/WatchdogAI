# EVALUATION STRATEGY AND METRICS

This section outlines the multi-faceted evaluation strategy designed to rigorously assess the performance, effectiveness, and usability of the integrated system. The evaluation is structured into four key areas: the performance of the anomaly detection model, the performance of the blockchain subsystem, the computational efficiency of the system, and the overall software quality based on the ISO/IEC 25010 standard.
III.9.1. Anomaly Detection Model Performance
The effectiveness of the Isolation Forest model in identifying anomalous procurement transactions was quantitatively assessed using a suite of standard classification metrics. These metrics were derived from a confusion matrix generated by comparing the model's predictions against the ground-truth labels in the test dataset.
a) Precision: Measures the proportion of correctly identified anomalies out of all transactions flagged as anomalous. It answered: "Of all the transactions we flagged as suspicious, how many were actually fraudulent?"
b) Recall (Sensitivity): Measures the proportion of actual anomalies that were correctly identified by the model. It answered: "Of all the actual fraudulent transactions, how many did we successfully detect?"
c) F1-Score: The harmonic mean of Precision and Recall, providing a single score that balances both concerns. This is particularly useful for evaluating performance on an imbalanced dataset where anomalies are rare.
d) Area Under the Receiver Operating Characteristic Curve (AUC-ROC): Measures the model's ability to distinguish between anomalous and normal transactions across all classification thresholds. An AUC value closer to 1.0 indicates a higher-performing model.
III.9.2. System Computational Efficiency
To evaluate the system's practicality and potential for scalability, its computational performance was measured under controlled conditions.
a) Analysis Response Time: The average time required for the system to process a dataset and return anomaly detection results. This was measured for varying dataset sizes (e.g., 100, 1,000, and 10,000 transactions) to assess performance scaling.
b) Feature Engineering and Price Scraping Latency: The time taken to execute the web-scraping module and integrate real-time price data for a standard batch of transactions.
III.9.3. Blockchain Subsystem Performance
The performance of the simulated blockchain environment was evaluated to demonstrate its efficiency and reliability in ensuring data integrity.
a) Throughput: The rate at which new transaction blocks were processed and appended to the blockchain, measured in Transactions Per Second (TPS).
b) Data Integrity Verification Time: The time required to perform a full audit of the blockchain. This involved traversing the chain from the genesis block to the latest block, verifying the cryptographic hash of each block against the previous_hash reference in the subsequent block. This was measured against varying blockchain lengths (e.g., 100, 1,000, and 10,000 blocks).
c) Tamper Detection Efficacy: The ability of the integrity verification component to detect unauthorized modifications. This was tested by intentionally altering the data of a single block within a valid chain and then executing the verification function to confirm that the system successfully identified the broken hash link, thereby flagging the chain as compromised.
III.9.4. Software Quality and Usability (ISO/IEC 25010)
The overall quality of the web-based application was evaluated using a structured survey administered to a group of target users. The survey instrument was designed based on the software quality characteristics defined in the ISO/IEC 25010 standard.
A questionnaire utilizing a 5-point Likert scale was developed to gather quantitative feedback on the following five characteristics: 
a) Functional Suitability: This was assessed by evaluating the core features of the system. Participants were asked to rate the system's ability to successfully upload procurement data, the effectiveness of the AI in detecting anomalies, the clarity and helpfulness of the XAI-generated explanations, and the correctness of the transaction display and blockchain status feedback.
b) Usability: This characteristic was measured by assessing the ease of use of the user interface. Questions focused on how easy the results dashboard was to understand, the clarity and readability of the data table, the intuitiveness of interactive tools like sorting and filtering, and the ease of navigation between different sections of the application.
c) Reliability: The stability of the application was evaluated by asking participants if the application ran smoothly without crashing or freezing, particularly during the AI analysis task. It also measured whether the system consistently provided clear success or error messages after an operation was performed.
d) Performance Efficiency: This was evaluated based on the perceived speed and responsiveness of the system. Participants rated how fast the application felt when sorting or filtering large data tables and whether the anomaly detection process was completed in what they considered a reasonable amount of time.
e) Security: The perceived security of the system was assessed by asking participants how secure the process of uploading transaction data felt and whether the inclusion of a simulated blockchain made the system feel more trustworthy.
III.9.5. Statistical Considerations
To ensure the validity of the evaluation results, appropriate statistical methods were employed.
a) Descriptive Statistics: Mean, median, and standard deviation were calculated for all quantitative performance metrics. This included the model's precision, recall, F1-score, and AUC-ROC values; the system's analysis response time and feature engineering latency; and the blockchain's throughput (TPS) and data integrity verification time.
b) Data Analysis for Survey: The Likert scale responses from the ISO/IEC 25010 survey were analyzed to determine the mean satisfaction score for each quality characteristic.
